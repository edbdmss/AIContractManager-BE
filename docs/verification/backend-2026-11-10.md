# 백엔드 통합 검증 — 2026-11-10

명령: `mvn clean test -Dmysql.integration=true`

## 검증 환경
- 로컬 MySQL 8.0에 매 실행 UUID 이름의 `acm_verify_...` 테스트 전용 DB 생성.
- 기존 개발 DB는 변경하지 않음. V1~V3 적용 후 기존 결제 감지 데이터를 삽입하고 V4 업그레이드 검증.
- Spring Boot 실제 컨텍스트, JDBC, JWT 보안 필터와 MockMvc API 호출을 사용.
- 임의 localhost 포트로 실제 HTTP 서버를 시작하여 인증 전/후 403/200 확인.
- FCM과 AI 외부 호출은 비활성화. 실제 OAuth 로그인·Gemini 응답·FCM 전달·Android 수집은 이번 검증 대상에 포함하지 않음.
- 종료 시 테스트 DB 삭제 후 information_schema에서 삭제 여부 확인. 테스트 서버는 Maven 종료와 함께 종료.

## 통합 시나리오 (14개)
1. V3→V4 마이그레이션, 기존 결제 이벤트 보존.
2. 결제 감지→월간 제안→알림→수락→계약 연결, 중복 수락 차단.
3. 미인증·미래 결제일·음수 금액 거절 및 저장 없음.
4. 금액/마감순 정렬, 잘못된 정렬값 거절, 타 사용자 조회·해지·삭제 차단.
5. 날짜 유지/변경 시 자동 일정 처리, 해지 후 알림 취소 및 금액 재확인 시 해지 유지.
6. 날짜 제거 후 같은 날짜 복원 시 알림 재생성.
7. 대시보드 자동 일정 중복 없음.
8. 삭제 후 상세 조회 404 및 대기 알림 취소.
9. 실제 HTTP 인증 전/후 접근.
10. 날짜 변경 후 원복과 재저장 시 중복 없음, 수동 일정 보존.
11. 일정 완료 시 알림 취소, 타 사용자 차단, 재완료 409.
12. 동일 결제 이벤트 동시 요청 시 한 건 저장.
13. 주간 간격 오탐 방지, 거절한 사업자 재제안 방지.
14. 미래 알림 숨김·읽음 제외, 예약 도래 알림 선점, 중복 선점 방지, 재시도 대기 및 발송 상태 저장.

## 발견 및 수정
- FCM 비활성화 시 FirebasePushSender가 필수 FirebaseMessaging 빈을 요구해 서버 기동 실패: 동일한 enabled 조건 적용.
- 날짜 삭제 후 복원 시 과거 일정 때문에 새 알림 누락: 교체된 자동 일정의 managed 표시 해제.
- 자동 일정과 계약 날짜가 캘린더에 중복 노출: 자동 일정이 존재하는 계약 날짜의 중복 합산 제외.

## 재실행
기존 application-local.yml의 로컬 MySQL 접속 설정을 사용한다. 테스트 계정에 임시 DB CREATE/DROP 권한이 필요하다. 기본 mvn test에서는 MySQL 통합 검증을 건너뛰며, 명시적으로 위 명령을 실행해야 한다. 접속 비밀값은 문서나 테스트 코드에 포함하지 않는다.
